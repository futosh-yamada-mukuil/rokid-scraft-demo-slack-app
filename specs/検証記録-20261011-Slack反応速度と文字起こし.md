# Slack版 反応速度・文字起こしの検証記録（2026-10-11）

## 結論

- Slackの返信が端末の通知に出るまでの時間は、同じ条件で **平均23.8秒 → 平均1.9秒**（最大34.4秒 → 最大2.9秒）になった。
- 実際のSlackワークスペースには読み取りだけで接続し、高速化の前提（チャンネル履歴の親投稿に `latest_reply` / `reply_count` が付くこと）と、3秒間隔の確認で利用制限に当たらないことを確認した。
- 実際のSlack（#開発用）へAVDから写真を1枚送り、スレッド返信が投稿からAVDの画面に出るまでを同じ条件で比べた。改善前の中継サーバは10〜20秒、改善後は2〜5秒（各3件）。
- AVD（arm64・Android 12・480×640）でアプリを起動し、端末登録・ロビー・撮影・コメント録音・送信・通知・記録一覧・設定を一通り操作して、クラッシュが無いことを確認した。
- 同梱の認識モデルをAVD上で動かし、日本語14文で文字誤り1/216、モデル読み込みの先読みで録音後の待ちが平均約1.05秒→約0.14秒（結果は同一）になることを確認した。モデルの生出力26文のうち従来の整形で空白が残っていた7文は、今回の整形で0文になった。
- 雑音だけの録音に実モデルが「.」「I.」「我.」を返す問題を見つけ、聞き取れなかったものとして扱うようにした（AVD上で雑音のみ10件: 文字が出る 10件→0件）。人の声の実録音（日・英・中・韓・広東語）は参照文どおりに認識された。
- **Rokid実機での動作は確認していない。** 下の「未確認」を参照。

## 1. 返信が通知に出るまでの時間（通し計測）

`bash scripts/verify-slack-relay-e2e.sh` で計測した。構成は次のとおり。

```text
端末側の本物のコード（JVM上）            実物の中継サーバ（別プロセス）        Slackの模擬
SlackAuth / SlackRelayClient      ⇄   app/api（HTTP・実時間）        ⇄   app/api/test/support/fake-slack.ts
TranslatedFeedRepository               slack-relay.ts / slack.ts          1呼び出し150msの遅延を模擬
TeamsChatNotificationViewModel
```

端末登録（8文字コード）→ 写真3枚の送信 → 人のスレッド返信 → 通知カードに返信が出るまで、を実時間で流す。返信の投入時刻は中継サーバの確認周期と揃わないよう乱数でずらす。翻訳は原文をそのまま返す代役（Googleキーなし）。

| 構成 | 返信→通知（ms） | 平均 | 最大 |
|---|---|---:|---:|
| 改善前: `codex/slack-avd`（067610e）の中継サーバ＋10秒ごとの定期取得 | 34392, 24683, 31374, 19996, 27430, 4629 | 23.8秒 | 34.4秒 |
| 改善後: 履歴による変化検知（3秒）＋変化待ちの取得 | 1797, 784, 2453, 2050, 764, 2882, 2830, 2148, 881, 2746 | 1.9秒 | 2.9秒 |

写真1枚の送信（端末→中継サーバ→模擬Slack）は平均955ms → 平均787ms。

改善前の値は仕様書に書かれていた「通常30〜40秒程度の遅延」と整合する。改善後の所要時間は「中継サーバがSlackを確認する周期（最大3秒）」が支配的で、Slackの応答がこの模擬（150ms）より遅ければその分だけ延びる。

改善前の計測は、旧版の `app/api/src` を取り出して同じ模擬・同じ端末側コード（変化待ちを無効化）で動かした。

```bash
mkdir -p .local/bench/old-api
git archive codex/slack-avd app/api/src | tar -x -C .local/bench/old-api --strip-components=2
ln -sfn "$PWD/app/api/node_modules" .local/bench/old-api/node_modules
API_SRC="$PWD/.local/bench/old-api/src" bash scripts/verify-slack-relay-e2e.sh legacy
```

## 2. 実際のSlackへの読み取り専用の確認

設定済みのワークスペース・プライベートチャンネルに対し、改善後の中継サーバを**読み取りAPIだけ**で動かした（`auth.test` / `conversations.info` / `conversations.history` / `conversations.replies` / `users.info`）。投稿・アップロードのAPIは呼んでいない。端末登録は状態ファイルの写しに対して行い、本文・投稿者・トークンは出力していない。

| 確認 | 結果 |
|---|---|
| 最初の取得 | HTTP 200、5件、1.5秒（監視中の5スレッドを読む初回のみ） |
| 履歴の形 | 返信のある親投稿4件すべてに `reply_count` と `latest_reply` が付いていた |
| 20秒間の変化待ち（誰も投稿しない） | 20.0秒後に同じ版で応答。その間のSlack呼び出しは `conversations.history` 6回のみ、`conversations.replies` は0回 |
| 利用制限（429） | 0回 |

これで、実際のSlackでも「変化が無い間はスレッドを読み直さない」ことと、履歴から新着返信を検知できる前提が成り立つことを確認した。

## 3. 文字起こし

端末でモデルを動かせなかったため、モデルが過去に実際に返した文字列を入力にして後処理を検証した（`TranscriptTextTest`）。

| 入力（実際の出力） | 出典 | 後処理の結果 |
|---|---|---|
| 現場 の 写真 を 確認 して ください。 | オフライン音声認識.md の比較表 | 現場の写真を確認してください。 |
| 请检查现场的照片。／Please check the photos from the site. | 同上 | 変更なし |
| 현장 사진 을 확인 해 주세요. | 同上・AVD実行ログ | 変更なし（韓国語の空白は保持） |
| こちらが現場の書真。 | 2026-10-04 に #開発用 へ投稿された文 | こちらが現場の写真。 |
| はい、こんにちは、よろしくお願い。／はい、よろしくお願いいたします。 | 同上 | 変更なし |

「エラー 発生」「しました。 送ります」のように長音・句読点の後ろへ残っていた空白は、従来の整形では消えないことをJVMで再現したうえで直した。

録音中のモデル先読みは、本物と同じ `PreparedResource` を使った仮想時間のテストで、読み込み4秒・認識0.3秒の認識器なら録音後の待ちが4.3秒 → 0.3秒になり、文字起こしは同じであることを確認した（`RecordedSpeechSourceTest`）。同梱モデルの実測値は、AVDでの1回の認識が3.7〜6.5秒（2026-10-04、読み込み・解放込み）、macOSでの内訳が読み込み0.9〜1.4秒・デコード0.08〜0.16秒（オフライン音声認識.md）。

## 5. AVD上での起動と基本機能（2026-10-11 追加）

AVD `Rokid_Verify`（arm64-v8a・Android 12 / API 32・480×640・240dpi）に `slackEmulator` のAPKを入れ、キー操作（↑↓・決定・戻る）で次を順に通した。最初は模擬Slack付きの中継サーバ（`SLACK_E2E_PORT=8787 node --experimental-strip-types scripts/slack-relay-e2e-server.ts`）、続けて実際のSlackに繋いだ中継サーバで行った。いずれも `FATAL EXCEPTION`・ANRは無かった。

| 操作 | 結果 |
|---|---|
| 起動 → Slack接続画面（8文字コード）→ PC側で承認 | ロビーへ自動で戻り「接続中」 |
| 操作メニュー → 写真送信 → 縦 → 撮影 | 1392×1856のJPEG。コメントの確認へ |
| コメント「はい」→ 5秒録音（AVDは音声入力なし） | 「マイクが音を拾えませんでした」→ やり直す／コメントなしで進む。録音中に先読みした認識器は解放された |
| 送信確認「はい」 | 模擬Slack・実際のSlackとも投稿成功（実Slackは端末側の計測で2.2秒） |
| スレッド返信 | 通知カードとロビーの吹き出しに表示 |
| 記録を見る／設定 | 表示・移動とも正常 |
| ロビーを開いたまま1分待つ | 経過時間が「たった今」→「1分前」に進む（投稿は増やしていない） |

実際のSlackでは、AVDから送った写真（bot投稿）のスレッドに【動作確認】の返信を3件送り、Slackの投稿時刻から画面で確認できるまでを測った。画面の文字取得（`uiautomator dump`）に約2.3秒かかるため、幅で示す。

| 返信 | 投稿から画面で確認できるまで |
|---|---|
| 1件目 | 2.6〜4.9秒 |
| 2件目 | 3.1〜5.4秒 |
| 3件目 | 2.1〜4.4秒 |

続けて、中継サーバだけを改善前のコード（`codex/slack-avd` の `app/api/src`）に差し替え、同じAVD・同じスレッドで同じ計測を行った。

| 返信 | 改善前の中継サーバ | 改善後 |
|---|---|---|
| 1件目 | 10.1〜12.8秒 | 2.6〜4.9秒 |
| 2件目 | 17.2〜19.6秒 | 3.1〜5.4秒 |
| 3件目 | 11.7〜14.1秒 | 2.1〜4.4秒 |

改善前の構成では、返信の時刻が30秒キャッシュのどこに当たるかで0〜40秒の幅が出る。3件の値はその範囲内で、模擬Slackでの6件（4.6〜34.4秒）とも整合する。

中継サーバのログに利用制限（429）は無かった。翻訳はGoogleキーが無いため「[翻訳できません・原文]」の表示。

### マイクからのコメント録音

AVDをMacのマイク入力ありで起動し、アプリの5秒録音中にMacのスピーカーから読み上げ音声を流して、録音 → 文字起こし → 送信確認の表示までを通した（空気を伝わった音をマイクで拾う経路）。録音は保存・送信していない。

| 再生 | 録音の最大振幅 | 結果 |
|---|---:|---|
| 「こちらが現場の写真です。」通常の音量 | 1161 | 「The.」（誤り） |
| 同じ文、再生音量を3倍 | 4475 | 「こちらが現場の写真です。」（正しい） |
| 以降4回 | 90〜170 | 「マイクが音を拾えませんでした」。途中でMacの音声出力が消音されたため無音だった |

- 録音・先読み・認識・画面表示の経路は端末上で動き、認識は先読み済みで0.16〜0.23秒だった。
- 小さく拾った音（最大振幅1161）は無音とは判定されず（しきい値500）、意味のない短い文字列になった。送信前の確認画面に文字起こしが出るので、利用者はそこで気づける。声が小さい・マイクから遠い場合の認識率は、この1件からは判断できない。
- 正しく認識できたのは1件だけで、人の声ではなく読み上げ音声である。

## 6. 同梱モデルのAVD上での認識（2026-10-11 追加）

macOSの読み上げで作った合成音声29件（日本語14文＋その音量を−20dB・−30dBに下げたもの12件、英・中・韓 各1文）を、`OfflineSttBenchDeviceTest` で認識した。マイクは使っていない。期待文との比較は句読点・空白を除いた文字単位。

| 区分 | 件数 | 文字誤り | 備考 |
|---|---:|---:|---|
| 日本語（通常の音量） | 14 | 1/216（0.5%） | 「締め直します」→「閉め直します」（同音） |
| 日本語 −20dB | 6 | 0/87 | |
| 日本語 −30dB | 6 | 1/87（1.1%） | 「閉めました」→「締めました」（同音） |
| 英語／中国語 | 各1 | 0 | |
| 韓国語 | 1 | 1/11 | 「해」の欠落（既知） |

- **音量**: 小さい音量でも結果はほぼ変わらなかった。入力音量の正規化は不要と判断した（入れていない）。
- **空白の整形**: 後処理前の生出力（`-e raw true`）26文のうち、従来の整形では7文に空白が残った（「エラー が発生して…」「センサー の交換が…」）。今回の整形では0文。英・中・韓の出力は変わらない。
- **所要時間**: 認識の直前にモデルを読み込む従来方式は平均約1.05秒（初回のみモデル展開込みで1.9秒）。録音時間ぶん前に先読みした場合は平均約0.14秒（10件、114〜226ms）。先読みの有無で文字起こしは一致した。
- **メモリ**: 先読みした認識器の保持中はPSS約343MB、解放後は約101MB。

合成音声は人の声・現場の騒音より認識しやすい。この数値は「後処理と先読みが端末上で正しく動く」ことの確認であり、実運用での認識率ではない。AVDはApple Siliconのホスト上で動くため、所要時間の絶対値もRokid実機とは異なる。

```bash
./gradlew :rokid:assembleDebug :rokid:assembleDebugAndroidTest \
  -PinstrumentationRunner=com.scraft.glassreport.capture.asr.OfflineSttBenchDeviceTest
adb install -r app/rokid/build/outputs/apk/debug/rokid-debug.apk
adb install -r app/rokid/build/outputs/apk/androidTest/debug/rokid-debug-androidTest.apk
# 16kHz/mono/PCM16 のWAVと manifest.tsv（ファイル名<TAB>期待文）を files/offline-stt-bench/ に置く
adb shell am instrument -w -e warm 10 \
  com.scraft.glassreport.test/com.scraft.glassreport.capture.asr.OfflineSttBenchDeviceTest
```

## 7. 雑音・小さい声・人の声の実録音（2026-10-11 追加）

マイクの確認で、小さく拾った音が「The.」になった。原因を調べるため、37件の音声をAVD上の実モデルに掛けた（`-e raw true` でモデルの生の出力と札を取得）。音声は、合成した雑音、既存の合成音声に雑音・残響を加えたもの、モデルの配布物に同梱されている人の声の実録音（`test_wavs/`）。

| 入力 | 件数 | 結果 |
|---|---:|---|
| 雑音だけ（白色・ピンク・50Hzハム、最大振幅300〜3000） | 10 | すべて `.` `I.` `我.` のいずれかを返した。札は `<\|en\|><\|EMO_UNKNOWN\|><\|Speech\|>` で、声と区別できない |
| 小さい声（最大振幅1200）＋雑音、SN比20〜0dB | 8 | すべて正しい |
| 通常の音量の声＋雑音、SN比10・5・0dB | 3 | 10・5dBは正しい。0dBで2文字誤り |
| 残響と高域減衰を加えた声（最大振幅1161 / 4475） | 4 | 3件正しい。1件で1文字誤り（配→体） |
| 話し始め・話し終わりが切れた声 | 2 | 始めが切れても正しい。終わりが切れると語尾が欠ける |
| 人の声の実録音（日・英・中・韓・広東語） | 5 | 参照文どおり（6秒を超える日・英は先頭5.9秒まで） |
| 同じ実録音を小さく＋雑音（SN比10dB） | 5 | 日本語で3文字誤り、ほかは正しい |

**直したこと**

- 雑音だけの録音は無音判定（最大振幅500）を超えることがあり、その場合 `.` や `I.` がそのままコメントとして確認画面に出て送信できていた。Rokidの環境音は実測で最大振幅246〜1341。句読点だけの出力と、`I` `我` `The` のようにそれだけでは何も伝えない出力は、聞き取れなかったものとして扱う（`TranscriptText.meaningful`）。画面は既存の「音声入力失敗」（録音やり直す／コメントなしで進む）になる。`好` `是` `네` `OK` `はい` のような短い返事は残す。
- 数字と和文の間の空白を詰める（`50 円` → `50円`、`2024 年 10 月` → `2024年10月`）。英語の `50 pieces` と韓国語の `50 원` は変えない。

修正後に同じ37件を掛け直した結果: 雑音のみ10件で文字が出たのは10件 → 0件。声の入った27件の結果は、数字の空白が詰まった以外は変わらない。

小さい声や雑音そのものでは認識はほとんど崩れなかった。マイクの確認で「The.」になったのは、スピーカーから出した音をマイクで拾う方法のため声がほとんど録音に残らなかったものと考えられる（再生音量を上げた回は正しく認識された）。

## 8. この確認で見つけて直したもの

- `scripts/create-rokid-avd.py` がホストのCPUを `platform.machine()` で判定していたため、Apple SiliconのMacでIntel版のPython（pyenv等）を使うとx86_64のAVDを作っていた。macOSではCPUそのものを確かめるようにした。
- 同スクリプトがarm64のAVDに `hw.cpu.arch=arm64-v8a` と書いており、Emulatorが起動を拒否していた（正しくは `arm64`）。
- 既存のAVDがホストと違うCPU用のとき、そのまま返して起動時に分かりにくいエラーになっていた。理由と対処を表示するようにした。
- `scripts/run-emulator.sh` に、Apple SiliconのMacでIntel版のEmulatorが入っている場合の案内を追加した。

作業に使ったMac（Apple M1 Max）は、Android EmulatorがIntel版・システムイメージがx86_64だけで、AVDを起動できない状態だった。Apple Silicon用のEmulator（37.2.12）とAndroid 12のarm64-v8aイメージを導入して確認した（Intel版は `~/Library/Android/emulator-intel-backup-20261011` に退避）。既存の `Rokid_Test` はx86_64用のため、このMacでは `ROKID_AVD_NAME=Rokid_Verify bash run.sh slack` のように別名のAVDを指定する。

## 未確認

- **Rokid実機での動作**: 実機は接続していない。上のAVD確認は実機と同じOS（Android 12）・画面サイズだが、カメラ・マイク・メモリ量・処理速度は実機と異なる。モデルの先読みは録音中のメモリ使用が増える（保持中 約343MB）ので、実機で1回録音して文字起こしまで通ることと、撮影画面へ戻ったときにカメラが再表示されることを確認してほしい。
- **人の声でのコメント録音**: マイク経由の確認は読み上げ音声で1件成功したところまで（上の表）。人が話した声、現場の騒音、Rokidのマイクでの認識率は測っていない。
- **認識モデルの精度**: モデル・言語設定・録音条件は変えていない。今回の改善は認識後の文字列に対するもので、「書真」以外の取り違え（上の「締め／閉め」など）には効かない。
- **Google翻訳・TTSを通した所要時間**: 検証環境にGoogleキーが無い。翻訳は1件あたりの通信時間が上の値に加わる。
