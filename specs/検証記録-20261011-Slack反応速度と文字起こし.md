# Slack版 反応速度・文字起こしの検証記録（2026-10-11）

## 結論

- Slackの返信が端末の通知に出るまでの時間は、同じ条件で **平均23.8秒 → 平均1.9秒**（最大34.4秒 → 最大2.9秒）になった。
- 実際のSlackワークスペースには読み取りだけで接続し、高速化の前提（チャンネル履歴の親投稿に `latest_reply` / `reply_count` が付くこと）と、3秒間隔の確認で利用制限に当たらないことを確認した。
- 文字起こしは、モデルが実際に返した出力とSlackへ実際に投稿された文を再生するテストで、整形と「書真→写真」の修正を確認した。
- **Rokid実機・AVD上の動作、実際のSlackへ新しい返信を投稿しての所要時間、認識モデルそのものの精度は確認していない。** 下の「未確認」を参照。

## 1. 返信が通知に出るまでの時間（通し計測）

`bash scripts/verify-slack-relay-e2e.sh` で計測した。構成は次のとおり。

```text
端末側の本物のコード（JVM上）            実物の中継サーバ（別プロセス）        Slackの模擬
SlackAuth / SlackRelayClient      ⇄   app/api（HTTP・実時間）        ⇄   app/api/test/support/fake-slack.ts
TranslatedFeedRepository               slack-relay.ts / slack.ts          1呼び出し150msの遅延を模擬
TeamsChatNotificationViewModel
```

端末登録（8文字コード）→ 写真3枚の送信 → 人のスレッド返信 → 通知カードに返信が出るまで、を実時間で流す。返信の投入時刻は中継サーバの確認周期と揃わないよう乱数でずらす。翻訳は原文をそのまま返す代役（Googleキーなし）。

| 構成 | 返信→通知（ms） | 平均 | 最大 |
|---|---|---:|---:|
| 改善前: `codex/slack-avd`（067610e）の中継サーバ＋10秒ごとの定期取得 | 34392, 24683, 31374, 19996, 27430, 4629 | 23.8秒 | 34.4秒 |
| 改善後: 履歴による変化検知（3秒）＋変化待ちの取得 | 1797, 784, 2453, 2050, 764, 2882, 2830, 2148, 881, 2746 | 1.9秒 | 2.9秒 |

写真1枚の送信（端末→中継サーバ→模擬Slack）は平均955ms → 平均787ms。

改善前の値は仕様書に書かれていた「通常30〜40秒程度の遅延」と整合する。改善後の所要時間は「中継サーバがSlackを確認する周期（最大3秒）」が支配的で、Slackの応答がこの模擬（150ms）より遅ければその分だけ延びる。

改善前の計測は、旧版の `app/api/src` を取り出して同じ模擬・同じ端末側コード（変化待ちを無効化）で動かした。

```bash
mkdir -p .local/bench/old-api
git archive codex/slack-avd app/api/src | tar -x -C .local/bench/old-api --strip-components=2
ln -sfn "$PWD/app/api/node_modules" .local/bench/old-api/node_modules
API_SRC="$PWD/.local/bench/old-api/src" bash scripts/verify-slack-relay-e2e.sh legacy
```

## 2. 実際のSlackへの読み取り専用の確認

設定済みのワークスペース・プライベートチャンネルに対し、改善後の中継サーバを**読み取りAPIだけ**で動かした（`auth.test` / `conversations.info` / `conversations.history` / `conversations.replies` / `users.info`）。投稿・アップロードのAPIは呼んでいない。端末登録は状態ファイルの写しに対して行い、本文・投稿者・トークンは出力していない。

| 確認 | 結果 |
|---|---|
| 最初の取得 | HTTP 200、5件、1.5秒（監視中の5スレッドを読む初回のみ） |
| 履歴の形 | 返信のある親投稿4件すべてに `reply_count` と `latest_reply` が付いていた |
| 20秒間の変化待ち（誰も投稿しない） | 20.0秒後に同じ版で応答。その間のSlack呼び出しは `conversations.history` 6回のみ、`conversations.replies` は0回 |
| 利用制限（429） | 0回 |

これで、実際のSlackでも「変化が無い間はスレッドを読み直さない」ことと、履歴から新着返信を検知できる前提が成り立つことを確認した。

## 3. 文字起こし

端末でモデルを動かせなかったため、モデルが過去に実際に返した文字列を入力にして後処理を検証した（`TranscriptTextTest`）。

| 入力（実際の出力） | 出典 | 後処理の結果 |
|---|---|---|
| 現場 の 写真 を 確認 して ください。 | オフライン音声認識.md の比較表 | 現場の写真を確認してください。 |
| 请检查现场的照片。／Please check the photos from the site. | 同上 | 変更なし |
| 현장 사진 을 확인 해 주세요. | 同上・AVD実行ログ | 変更なし（韓国語の空白は保持） |
| こちらが現場の書真。 | 2026-10-04 に #開発用 へ投稿された文 | こちらが現場の写真。 |
| はい、こんにちは、よろしくお願い。／はい、よろしくお願いいたします。 | 同上 | 変更なし |

「エラー 発生」「しました。 送ります」のように長音・句読点の後ろへ残っていた空白は、従来の整形では消えないことをJVMで再現したうえで直した。

録音中のモデル先読みは、本物と同じ `PreparedResource` を使った仮想時間のテストで、読み込み4秒・認識0.3秒の認識器なら録音後の待ちが4.3秒 → 0.3秒になり、文字起こしは同じであることを確認した（`RecordedSpeechSourceTest`）。同梱モデルの実測値は、AVDでの1回の認識が3.7〜6.5秒（2026-10-04、読み込み・解放込み）、macOSでの内訳が読み込み0.9〜1.4秒・デコード0.08〜0.16秒（オフライン音声認識.md）。

## 未確認

- **Rokid実機・AVD上の動作**: 作業に使ったMac（Apple M1 Max）ではAVDを起動できなかった。入っているAndroid EmulatorがIntel版（`darwin-x86_64`）、システムイメージもx86_64だけで、ハードウェア仮想化の初期化に失敗する（`failed to initialize HVF`）。ソフトウェア実行（`-accel off`）は25分待っても起動しなかった。このMacで動かすには、Android StudioのSDK ManagerでApple Silicon用のEmulatorとarm64-v8aのシステムイメージを入れる必要がある。カメラ・録音・JNIの認識器・画面表示は端末で動かしていない。特にモデルの先読みは認識器を作るタイミングが変わるので、`bash run.sh slack` で1回録音して文字起こしまで通ることを確認してほしい。AVD操作ボタンのキー送出も経路を変えた（`window.decorView` 経由）。
- **実際のSlackでの新着返信**: 実チャンネルへの投稿が必要なため行っていない。読み取り専用の確認と模擬Slackでの通し計測までである。
- **認識モデルの精度**: モデル・言語設定・録音条件は変えていない。今回の改善は認識後の文字列に対するもので、「書真」以外の取り違えには効かない。入力音量の正規化は、端末の音声で測れないまま入れると雑音を誤認識する恐れがあるため見送った。
- **Google翻訳・TTSを通した所要時間**: 検証環境にGoogleキーが無い。翻訳は1件あたりの通信時間が上の値に加わる。
