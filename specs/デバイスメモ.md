# Rokid Glasses デバイスメモ

実機開発で詰まった点と仕様。次に触る人向けの備忘。

## デバイス諸元（確認値）
| 項目 | 値 |
|---|---|
| model | `RG-glasses`（`ro.product.model`）、OEM `RV101` |
| OS | YodaOS-Sprite（Android 12 / API 32） |
| CPU | arm64-v8a、画面密度 240dpi |
| ディスプレイ | 単眼・グリーン単色・低解像度。**正位置は portrait（480×640 相当 / ROTATION_0）** |
| ランチャー | `com.rokid.os.sprite.launcher` |
| サービス | `cxr-service`（CXR SDK）稼働 |
| 仕向け | **中国国内版**（`ro.product.rokid.oem.id=101` / ロケール `zh-CN`）。**GMS 非搭載** |

## ① インストールロック（最重要）
`adb install` は Rokid が `PackageManager` に入れた独自フックで
**`error: not allow package install!`** と拒否される。

- adb 通信自体は通る（device 認識・getprop 等の読み取り系は動く）が、インストール認可は別。
- PC 側からは解除不可：`development_settings_enabled=1` 化、`settings put`、`setprop` いずれも無効
  （`wm` / `cmd` / 大容量 `push` / `setprop` は `error: closed` で弾かれる）。
- **解除**：スマホの「Hi Rokid」アプリ → グラスとペアリング → 設定 → 開発者 →
  「ADB デバッグ」を ON。これで `adb install -r` が通る。

## ② 画面の向き
- ランチャーは **portrait / ROTATION_0**（480×640）。これが装着時の正位置。
- アプリに `android:screenOrientation="landscape"` を指定すると ROTATION_90 になり
  **画面が 90°傾く**。`nosensor` でも landscape 化した。
- **対策：全 Activity で `android:screenOrientation="portrait"` を明示**。
- レイアウトは縦長前提（中央寄せ・縦積み）で設計する。

## ③ 近接センサーで画面 OFF
- `rokid.psensor.mode=sensitive`。**未装着時はディスプレイが消灯**し、`screencap` が真っ黒になる。
- 実機の目視確認は装着して行う。UI だけの確認はエミュレータ `Rokid_Glasses` が早い。
- アプリ側の含意：定期ポーリングは `Lifecycle.repeatOnLifecycle(STARTED)` の中で回せば、
  画面が消えている間は自然に止まる。

## ④ 入力（テンプルのタッチパッド）

実装は **`core/input/GlassControls.kt`（Compose の Modifier）と `core/input/TapArbiter.kt`
（タップ判定の純粋ロジック）の2ファイルだけ**。仕様は `core/input/TapArbiterTest.kt` に
固定してあるので、定数を触るときはテストごと直すこと。

### アプリに届くのは DPAD キーだけ
- スワイプは DPAD キーとして届く（上=KEYCODE 19、左=21 等）。`glassControls` は
  `onPreviewKeyEvent` **しか見ていない**（ソースにポインタ入力の配線は無い）。
  - 上/左 → `onUp`、下/右 → `onDown`、`DirectionCenter` / `Enter` / `NumPadEnter` → タップ。
  - タップは `onTouchEvent`（ACTION_DOWN）でも拾えるが、経路を1本に絞るため使っていない。
- キーイベントには**指の位置も移動量も速度も載っていない**。
- **含意**: 慣性スクロールや加速スクロールのような「スマホと同じ操作感」は
  **原理的に作れない**。1 操作＝1 ステップ送りの UI に寄せる（Feed の1件送り、メニューの1行移動）。

### 1スワイプで複数キーが飛ぶ → 移動は 250ms デバウンス
- 1 回のスワイプで LEFT+UP のように**複数キーが連続送出**され、素通しだと項目が数個飛ぶ。
- `GlassControls.kt` の `DEBOUNCE_MS = 250L` と `lastMove` カウンタで 1 操作に集約する。
- **含意**: 移動は最速でも 250ms に 1 回。長いリストをスワイプで走査させる設計にしない
  （1 画面の項目は数個に抑える）。

### 上下と左右は区別していない
- 上と左を `onUp`、下と右を `onDown` に**まとめている**。結果、
  **区別できるのは タップ / 前スワイプ / 後スワイプ の 3 つだけ**。
- **含意**: 1 画面のアクションは 3 つ以内に収める。4 つ目が要るなら画面を分けるか、
  「タップ＝値を巡回」のように**意味を状態に持たせる**（設定画面がその形）。

### 長押しは使えない。代替はダブルタップ
- 長押しは**システムの AI アシスタントが起動**してしまうので使わない（アプリ側では抑止できない）。
- 代替として `glassControls(onDoubleSelect = …)` を**渡した画面だけ**ダブルタップが有効になる。
  判定の有無は既定値の空ラムダ `NO_DOUBLE_TAP` と**同一インスタンスか**（`!==`）で切り替える。
- **全画面で意味は「1階層戻る」に統一**してある（BACK キーと同じ）。画面ごとに戻り方が変わると
  操作を覚えられないため。認証画面だけは「戻る＝サインインを飛ばす」なので `onSkip` を渡す。
- **含意**: ダブルタップを入れた画面は、**シングルタップが 300ms 遅れる**。撮影画面のシャッターと
  設定画面の値巡回はその分だけ反応が鈍い。一貫性と即応のトレードオフで、いまは一貫性を選んでいる。
  シャッターの即応を優先するなら撮影画面だけ外す判断もありうる。

### ダブルタップを有効にするとシングルが遅れる／定数が3つ要る理由
`TapArbiter.kt` の 3 つの定数は**役割が全部違う**。1 つにまとめると壊れる。

| 定数 | 値 | 役割 |
|---|---|---|
| `TAP_DEBOUNCE_MS` | 250ms | ダブルタップ**無効**の画面のタップのデバウンス。この経路はシングルを**即発火**する（シャッターを遅らせない） |
| `TAP_BOUNCE_MS` | 80ms | ダブルタップ**有効**時、1 回の物理タップで複数キー（`DPAD_CENTER` と `ENTER` 等）が届く分を潰す窓 |
| `DOUBLE_TAP_WINDOW_MS` | 300ms | 2 回目をダブルタップとみなす窓。**シングルはこの窓ぶん遅れて発火する** |

- **`TAP_BOUNCE_MS` に 250ms を流用してはいけない**。人が打つダブルタップの間隔は
  実測でおよそ **120〜250ms** なので、まるごとデバウンスに吸われて
  **2 回目のタップが永久に届かない**。だから「同一タップの重複イベントだけ」を潰せる
  短い窓（80ms）に分けてある。この失敗は
  `TapArbiterTest.doubleTapIsNotSwallowedByTheMoveDebounce` が固定している。
- 移動側の `DEBOUNCE_MS`（250ms）とタップ側の `TAP_DEBOUNCE_MS`（250ms）は
  **名前も値も紛らわしいが別のカウンタ**で、互いに干渉しない。
- シングルは即発火せず `TapDecision.HoldSingle` として保留し、窓が明けたあと
  `consumeHeldSingle(id)` が true を返したときだけ発火する（間に 2 回目が来ていれば破棄）。
  遅れて届いた古い保留が新しい保留を消さないよう、保留には連番 id を振ってある。
- **含意**: タップの反応速度が要る画面（シャッター・値の巡回）にダブルタップを足すと
  **300ms 鈍る**。足す前に「この画面のシングルタップは 300ms 遅れてよいか」を必ず確かめる
  （設定画面で渡していない理由は ⑭）。

### Rokid の SDK は使っていない
- `app/rokid/build.gradle` の `dependencies` に Rokid の依存は **1 つも無く**、
  `app/rokid/src` に `com.rokid` の import も **0 件**。`settings.gradle` に
  `maven.rokid.com` のリポジトリ定義だけが「後から足す場合用」に残っている。
- そもそも CXR SDK にタッチパッドの低レベル入力を開放する機能は無い（⑨）。
- **含意**: 入力の作り込みは**上記 2 ファイルの中で完結する**。
  「SDK を入れればスワイプ速度が取れる」という当てにはしない。

# 実機調査で分かったこと（2026-08 / Teams 連携アプリの検討時）

「グラス単体でできること」を期待して調べた結果、**できないことが多数判明**した。
本アプリがクラウド API 直叩きの構成になっているのはこの調査結果が理由である。

## ⑤ 標準の音声認識・音声合成が使えない
- **`SpeechRecognizer` のサービスが 1 つも登録されていない**。
  `RecognitionService` を提供するパッケージが端末に存在せず、`isRecognitionAvailable()` は false。
- **`TextToSpeech` のエンジンも 1 つも登録されていない**。GMS 非搭載（中国国内版）のため
  Google 音声認識／Google TTS がそもそも入っていない。
- **含意**: 音声認識も読み上げも**クラウド API を自前で叩くしかない**
  （本アプリでは AmiVoice と Google Cloud TTS を使用）。

## ⑥ ウェイクワード検出は非開放
- 「Hi Rokid」等のウェイクワード検出は **NXP RT600 コプロセッサ上のファームウェア**で動いており、
  サードパーティアプリには API が公開されていない。
- **含意**: **ボイスコマンドによる撮影トリガーは実装できない**。お客様仕様書の
  「ボイスコマンドまたはタップ」は**タップのみ**になる（仕様変更として客に戻す）。

## ⑦ LED は一般アプリから制御できない
- `/sys/class/leds/*` は `0640 system:system`。一般アプリのユーザでは読み書き不可。
- binder 経由の `lights_ctrl` サービスも **SELinux で遮断**されており呼べない。
- ただし**カメラ動作中は OS 側が白 LED を自動点灯**させる（撮影時の周囲への告知は結果的に行われる）。
- **含意**: 「完了を LED で通知」は実装できない。**シャッター音＋画面表示で代替**する
  （仕様変更として客に戻す）。

## ⑧ Rokid 内蔵 TTS（使わない方針）
- `com.rokid.os.sprite.tts.TtsService` が **exported で存在する**ことは確認できた。
- しかし **AIDL インターフェースが難読化**されており、安定して呼べる保証がない。
- **含意**: 今回は**使わない**。Google Cloud TTS に統一する（日英の声を切り替えられる利点もある）。

## ⑨ CXR SDK
- `maven.rokid.com`（`https://maven.rokid.com/repository/maven-public/`）から**認証なしで取得できる**。
- ただし本案件で使える機能は実質無い（ペアリング済みスマホとの連携が主目的で、
  カメラ・音声・LED の低レベル制御を開放するものではない）。
- Wi-Fi 側載ツール [RokidApkUploader](https://github.com/Miniontoby/RokidApkUploader) は CXR-M SDK 経由で、
  シリアル番号だけで APK を送り込める（`adb` が使えない場面の代替）。

## ⑩ 仕向け（中国国内版）
- `ro.product.rokid.oem.id=101` / ロケール `zh-CN`。海外版は OEM 105。
- 手元の実機はこのまま使用する方針だが、**海外版で運用するなら ⑤〜⑧ は再検証が必要**
  （GMS 搭載なら標準 TTS/STT が使える可能性がある）。

## ⑪ カメラは1個。CameraX の `CameraValidator` 警告は無視してよい
起動時に必ず次の警告が出るが、**この端末では正常**。直後に背面カメラは開く。

```
W CameraValidator: No available camera can be found. Cams:1 Id:0  Lens:1 ... LensFilter:0
W CameraX : CameraValidator$CameraIdListIncorrectException: Expected camera missing from device.
```

- CameraX が起動時に「前面・背面の両方があるか」を検証するもの。**グラスは背面1個しか持たない**
  （`Cams:1` / `Lens:1`＝背面のみ、`LensFilter:0`＝前面を探している）。
- W レベルで非致命。成功の判定は `Camera2ClientBase: Camera 0: Opened. Client: <package>` を見る。
- **含意**: このスタックトレースを見て「カメラが壊れた」と誤診しない。

## ⑫ `screencap` にカメラプレビューは写らない
プレビュー中に `screencap` を撮ると**プレビュー領域は真っ黒**になる（HUD や重ねた UI だけ写る）。
ハードウェアオーバーレイのため取得できない。

- **含意**: 黒い＝カメラが動いていない、ではない。動作確認は logcat で行う:
  - オープン: `Camera2ClientBase: Camera 0: Opened`
  - 撮影: `ImageCapture: takePictureInternal` → `ProcessingRequest: onImageCaptured: request ID = N`
- **撮影後**は結果画像が UI に出るので `screencap` に写る（サムネイル・寸法・バイト数まで確認できる）。

## ⑬ 旧アプリが端末に残っていると検証を取り違える
前身の `com.scraft.glassdemo`（バイタル記録デモ）が入ったままの端末がある。
**前面にいると `adb shell input keyevent` を奪われ、旧アプリのカメラログを新アプリのものと誤読する。**

実際に一度これで誤診しかけた。検証前に必ず前面を確かめる:

```bash
adb shell am force-stop com.scraft.glassdemo
adb shell dumpsys activity activities | grep topResumedActivity
```

`MainActivity` は `--es start <route>` で目的の画面へ直接飛べる（`home` / `capture` / `feed` / `settings` / `readback`）。
**ネットワーク未接続だと起動時に認証画面で止まる**ので、UI 確認はこれで飛ばすのが早い。

```bash
adb shell am start -n com.scraft.glassreport/.MainActivity --es start capture
```

## ⑭ 実測値（2026-08-16 / Gradle 9・AGP 9・CameraX 1.6.1 で確認）
| 項目 | 値 |
|---|---|
| 静止画（設定「1920」） | **960x1280 / 161KB** |
| compileSdk 37 のバイナリ | **API 32 実機で正常動作**（FATAL 0件） |
| 設定画面の戻る手段 | 「戻る」行のタップ か BACK キー。**ダブルタップでは戻れない** |

設定画面だけ `glassControls` に `onDoubleSelect` を渡していない。タップが「値の巡回」なので、
ダブルタップを有効にすると**シングルタップが判定窓ぶん遅れて値の切り替えが鈍る**ため意図的にそうしている。
